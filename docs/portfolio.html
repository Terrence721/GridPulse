Why this project

The architecture was written down before a line of service code was

The domain — utility metering and billing — is deliberately chosen, but the pipeline shape generalizes to any high-volume telemetry-to-billing system: IoT sensor networks, subscription usage billing, order processing. The full architecture, service breakdown, Kafka event contracts, and cross-cutting concerns (resiliency, idempotency, tracing, security, testing) were designed and documented up front, before any of it was built.

.NET 10 .NET Aspire 13 Kafka React 19 Redux Toolkit / RTK Query TimescaleDB / Postgres Node.js GitHub Actions OpenTelemetry

Built one phase at a time, in the open

Six phases, staged deliberately — the core domain loop first, Kafka and the dashboard later

Phase 1 — a direct-REST core loop (Meter Simulator → Usage Aggregation → Billing) on a single Postgres database — is done: real HTTP calls, real Postgres persistence, 37 tests passing, and an automated end-to-end smoke test that spins up the real stack. Kafka, a polyglot Node.js Notification Service, a React/Redux Toolkit dashboard, CI/CD, and full observability are layered in next, one phase at a time, scaffolded one file or folder at a step with nothing batched ahead of review.

Why event-driven, not a monolith

Independent scaling of ingestion vs. billing, a natural audit trail of events, and the ability to add new consumers later without touching the producers — reasoning recorded in the design doc, not asserted after the fact.

Tracked before it was built

A wiki, a GitHub project board (Backlog/Planned/In Progress/Verification & QA/Done), and this working log all went live during Phase 1's scaffolding — not retrofitted once there was something to show.

Nine real bugs, found by actually running the thing

All logged in todo.md, checkable against the commit history

From CodeQL failing before any service existed, to a live DNS resolution bug caught only by running the real distributed app end-to-end, to .NET 10 SDK/xUnit v3 tooling breakage — every one of these was found by actually building and running the thing, not by inspection.

01
.github/workflows/codeql.yml
CodeQL's JavaScript/TypeScript extractor hard-fails database finalize when it finds zero matching files — it does not just report zero findings the way build-mode: none does for a language that does have source present. Fixed by dropping javascript-typescript until real JS/TS code exists (Phase 3+) and adding csharp instead, once real C# source (ServiceDefaults) landed.
real CI failure · tooling issue #3
02
src/AppHost/GridPulse.AppHost.csproj
The csharp fix above then failed its own build: Aspire 13's AppHost SDK requires the Aspire CLI bundle to compile at all (ASPIRE009), and hosted GitHub runners don't have it. See the Judgment Calls section below for how this one was actually fixed rather than just patched over.
real CI failure · tooling issue #3
03
GitHub Security overview page
After both fixes above landed, the Security tab kept showing a "Code scanning configuration error" banner anyway. Root cause: GitHub's tool-status tracker doesn't clear a language just because a later workflow stops analyzing it — 7 failed /language:javascript-typescript analyses from the original broken runs were still sitting there, permanently "errored," with nothing superseding them. Fixed by deleting all 7 via the code-scanning API directly.
real finding · stale state, not live code issue #3
04
src/AppHost/AppHost.cs
The first live run of Meter Simulator → Usage Aggregation sent 0 of 7 readings successfully — every attempt failed with No such host is known (usage-aggregation:80). AppHost.cs registered meter-simulator without .WithReference(usageAggregation), so Aspire never injected the service-discovery config the DNS name needed to resolve. Caught only because the run was actually verified against real output instead of trusting a clean build — fixed, then re-verified live: 1,876/1,876 readings delivered.
real bug · live E2E only issue #6
05
global.json
Adding the first test project revealed that dotnet test is outright broken for xUnit v3 on the .NET 10 SDK ("VSTest target is no longer supported") unless a project opts into the new Microsoft.Testing.Platform runner mode — a repo-root global.json setting most guides don't mention yet, since it's brand new with .NET 10.
real tooling break · .NET 10 SDK issue #16
06
tests/UsageAggregation.Tests/*.csproj
Adding EF Core's InMemory provider for fast unit tests alongside the real Npgsql provider produced an unresolved Microsoft.EntityFrameworkCore.Relational version conflict — the app's own EF Core Design package forced 10.0.12 while the test project's transitive Npgsql dependency settled on 10.0.11. Fixed by pinning the version explicitly rather than ignoring the warning.
real dependency conflict issue #17
07
src/MeterSimulator/GridPulse.MeterSimulator.csproj
The hand-written .csproj used Microsoft.NET.Sdk.Worker alone, which doesn't pull in Microsoft.Extensions.Hosting as a framework reference — Host.CreateApplicationBuilder/BackgroundService/ILogger<T> all failed to resolve, 7 compile errors from one missing package reference.
real build failure issue #6
08
src/MeterSimulator/Program.cs
Fail-fast config validation worked — the app exited non-zero with a clean message — but a full stack trace printed first anyway. .NET's Generic Host logs OptionsValidationException internally during its own StartAsync(), before any caller's try/catch ever sees it. Fixed by resolving the options manually before host.Run(), so validation happens in application code, never reaching the Host's internal failure logging.
real bug · noisy failure path issue #6
09
tests/AppHost.Tests/Phase1SmokeTests.cs
Right after declaring Phase 1 done, re-running the smoke test a second time failed: Expected: 10, Actual: 50. The test used a hardcoded meter ID against AppHost's Postgres, which uses a persistent data volume by design for real local dev — so every run kept adding its reading to the same row left over from the last one. Fixed by generating a unique meter ID per run; re-verified by running it twice in a row against the same persistent database.
real bug · test isolation issue #10

Judgment calls

Where the interesting decisions actually happened

The AppHost build failure above was first worked around with a solution filter excluding AppHost from the CI build entirely — a legitimate pattern, already used for the same Aspire-13 issue on eshop-full. But AppHost.cs was about to gain real orchestration logic (the Postgres resource wiring) worth actually building and analyzing, not quietly excluding forever. That filter was reverted in favor of installing the real Aspire CLI in CI instead, pinned to the exact version the NuGet packages use — a few extra seconds per run, in exchange for CI building and CodeQL-analyzing the actual, complete solution instead of a narrower stand-in for it.
