Why this project

The architecture was written down before a line of service code was

The domain — utility metering and billing — is deliberately chosen, but the pipeline shape generalizes to any high-volume telemetry-to-billing system: IoT sensor networks, subscription usage billing, order processing. The full architecture, service breakdown, Kafka event contracts, and cross-cutting concerns (resiliency, idempotency, tracing, security, testing) were designed and documented up front, before any of it was built.

.NET 10 .NET Aspire 13 Kafka React 19 Redux Toolkit / RTK Query TimescaleDB / Postgres Node.js GitHub Actions OpenTelemetry

Built one phase at a time, in the open

Six phases, staged deliberately — the core domain loop first, Kafka and the dashboard later

Phase 1 is a direct-REST core loop (Meter Simulator → Usage Aggregation → Billing) on a single Postgres database — get the domain logic right before introducing an event bus. Kafka, a polyglot Node.js Notification Service, a React/Redux Toolkit dashboard, CI/CD, and full observability are layered in afterward, one phase at a time, scaffolded one file or folder at a step with nothing batched ahead of review.

Why event-driven, not a monolith

Independent scaling of ingestion vs. billing, a natural audit trail of events, and the ability to add new consumers later without touching the producers — reasoning recorded in the design doc, not asserted after the fact.

Tracked before it was built

A wiki, a GitHub project board (Backlog/Planned/In Progress/Verification & QA/Done), and this working log all went live during Phase 1's scaffolding — not retrofitted once there was something to show.

Three real CI failures, found and fixed before any service existed

All logged in todo.md, checkable against the commit history

Setting up CodeQL on a repo with almost no source yet surfaced genuine tooling failures — not hypothetical edge cases, actual red CI (and one silently-stale green banner).

01
.github/workflows/codeql.yml
CodeQL's JavaScript/TypeScript extractor hard-fails database finalize when it finds zero matching files — it does not just report zero findings the way build-mode: none does for a language that does have source present. Fixed by dropping javascript-typescript until real JS/TS code exists (Phase 3+) and adding csharp instead, once real C# source (ServiceDefaults) landed.
real CI failure · tooling issue #3
02
src/AppHost/GridPulse.AppHost.csproj
The csharp fix above then failed its own build: Aspire 13's AppHost SDK requires the Aspire CLI bundle to compile at all (ASPIRE009), and hosted GitHub runners don't have it. See the Judgment Calls section below for how this one was actually fixed rather than just patched over.
real CI failure · tooling issue #3
03
GitHub Security overview page
After both fixes above landed, the Security tab kept showing a "Code scanning configuration error" banner anyway. Root cause: GitHub's tool-status tracker doesn't clear a language just because a later workflow stops analyzing it — 7 failed /language:javascript-typescript analyses from the original broken runs were still sitting there, permanently "errored," with nothing superseding them. Fixed by deleting all 7 via the code-scanning API directly.
real finding · stale state, not live code issue #3

Judgment calls

Where the interesting decisions actually happened

The AppHost build failure above was first worked around with a solution filter excluding AppHost from the CI build entirely — a legitimate pattern, already used for the same Aspire-13 issue on eshop-full. But AppHost.cs was about to gain real orchestration logic (the Postgres resource wiring) worth actually building and analyzing, not quietly excluding forever. That filter was reverted in favor of installing the real Aspire CLI in CI instead, pinned to the exact version the NuGet packages use — a few extra seconds per run, in exchange for CI building and CodeQL-analyzing the actual, complete solution instead of a narrower stand-in for it.
