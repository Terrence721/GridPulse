GridPulse — Real-Time Event-Driven Utility Monitoring & Billing Platform

Design Document v1.0

Author: Terrence Daniels
Purpose: Original flagship portfolio project demonstrating principal-level system design, event-driven architecture, full-stack delivery, and DevOps/observability maturity.

1. Overview

GridPulse is a self-contained, event-driven platform that simulates a utility company's meter-reading, usage-aggregation, and billing pipeline. It is designed to be small enough to build solo in a reasonable timeframe, but architecturally deep enough to demonstrate the skills a Principal Developer role expects: distributed systems design, microservices decomposition, event streaming, resilient service-to-service communication, CI/CD, and production-grade observability.

The domain (utility metering/billing) is chosen deliberately to align with conversations already in progress with energy-sector employers, but the architecture generalizes to any high-volume telemetry-to-billing pipeline (IoT sensor networks, subscription usage billing, order processing, etc.), which is worth mentioning in interviews to show the design isn't domain-locked.

1.1 Goals

  • Demonstrate original architecture and decision-making, not a cloned reference app.
  • Exercise the real stack you'd use on the job: .NET Core / .NET Aspire, React + TypeScript + Redux Toolkit, Kafka, GitHub Actions CI/CD, New Relic-style observability.
  • Produce enough surface area (multiple services, an event bus, a UI, a pipeline, dashboards) to sustain a 30–45 minute deep-dive technical interview conversation.
  • Be deployable end-to-end (even if just to a local Kubernetes cluster or a single cloud VM) so you can demo it live rather than just describe it.

1.2 Non-Goals

  • Not a commercial-grade billing system — no real payment processing, no regulatory compliance (NERC/FERC, etc.).
  • Not optimized for massive scale — the point is to demonstrate correct patterns, not to handle millions of meters.
  • Not a mobile app — web dashboard only.

3. Service Breakdown

3.1 Meter Simulator

  • Lightweight .NET worker service that generates synthetic meter readings at a configurable interval and publishes them to Kafka.
  • Stands in for real IoT hardware — makes the whole system runnable without physical devices.

3.2 Usage Aggregation Service

  • Consumes raw readings, validates them (out-of-order detection, duplicate detection using idempotency keys), and rolls them into time-bucketed usage records.
  • Storage: TimescaleDB (Postgres extension) — a good opportunity to show you know time-series data modeling, which is directly relevant to utility/energy data.

3.3 Billing Service

  • Consumes aggregated usage, applies a rate plan (flat rate, tiered, time-of-use), and generates invoices.
  • This is where you can demonstrate domain modeling with proper OOP/SOLID design (rate plan as a strategy pattern, for example) — ties directly to your stated OOP/SOLID strengths.

3.4 Notification Service (Node.js)

  • Intentionally built in Node.js rather than .NET to demonstrate polyglot microservices competency and consistent event-contract design across language boundaries (a common enterprise reality, and a good discussion point given your Node.js background).

3.5 Account/Customer Service

  • Simple CRUD REST service for customer and meter registration.
  • Keeps the "boring" parts of the system properly separated from the event-driven core.

3.6 BFF / API Gateway

  • Backend-for-frontend that aggregates data from the above services for the React dashboard, and handles authentication (OIDC via an identity provider like Keycloak or Auth0 for demonstration).

3.7 React + Redux Toolkit Dashboard

  • Real-time usage charts (via WebSocket or SignalR push from the gateway), invoice history, and account management screens.
  • Redux Toolkit used for state management, with RTK Query handling data fetching/caching — playing the same role NgRx Effects would in an Angular app — to demonstrate the same pattern you'd use in a production React app.

4. Event Contracts (Kafka Topics)

TopicProducerConsumer(s)Schema (key fields)
meter.readings.raw Meter Simulator Usage Aggregation meterId, timestamp, kwh, readingId (idempotency key)
usage.aggregated Usage Aggregation Billing accountId, periodStart, periodEnd, totalKwh
billing.invoice.generated Billing Notification invoiceId, accountId, amountDue, dueDate

Use Avro or JSON Schema with a schema registry (Confluent Schema Registry, or a lightweight self-hosted alternative) to demonstrate schema evolution discipline — a detail that separates "used Kafka in a tutorial" from "understands operational Kafka."

5. Cross-Cutting Concerns

  • Resiliency: Polly-based retry policies and circuit breakers on inter-service HTTP calls; consumer-side dead-letter topics for poison messages.
  • Idempotency: Every event carries a unique ID; consumers track processed IDs to guard against at-least-once delivery duplicates.
  • Distributed tracing: OpenTelemetry instrumentation across all services, exported to a local Jaeger instance or New Relic (ties directly to your stated New Relic experience).
  • Security: OIDC-based auth at the gateway; secrets managed via environment variables/user-secrets locally and a vault-style secret store in the deployed environment.
  • Testing strategy:
    • Unit tests (xUnit for .NET, Vitest for the Node service and the React dashboard, React Testing Library for component behavior) — ties to your existing testing framework experience.
    • Contract tests for Kafka event schemas.
    • Integration tests using Testcontainers to spin up real Kafka/Postgres instances in CI.

6. CI/CD Pipeline (GitHub Actions)

  1. Build & test — per-service matrix build, unit + contract tests.
  2. Static analysis — integrate a linter/analyzer (SonarCloud free tier or built-in .NET analyzers) — ties to your stated static analysis experience.
  3. Container build — Docker images per service, pushed to GitHub Container Registry.
  4. Deploy — GitHub Actions deploys to a local k3s/minikube cluster for demo purposes, or to a single cloud VM via Docker Compose for simplicity.
  5. Post-deploy smoke test — automated health-check hitting each service's /health endpoint.

7. Observability

  • OpenTelemetry traces + metrics from every service.
  • A New Relic free-tier account (or Grafana/Prometheus if you'd rather stay fully open-source) with a dashboard showing: Kafka consumer lag, request latency per service, invoice-generation throughput, and error rates.
  • This is one of the most valuable parts of the project for a Principal interview — most portfolio projects stop at "it works," very few show "and here's how I'd know if it broke in production."

8. Suggested Build Phases

  1. Phase 1 — Core loop, no Kafka: Meter Simulator → Usage Aggregation → Billing, all via direct REST calls, single Postgres DB. Get the domain logic right first.
  2. Phase 2 — Introduce Kafka: Replace REST calls between services with Kafka topics. Add schema registry.
  3. Phase 3 — Add the Node.js Notification Service and Account Service.
  4. Phase 4 — Build the React/Redux Toolkit dashboard and BFF gateway.
  5. Phase 5 — CI/CD, containerization, and deployment automation.
  6. Phase 6 — Observability (OpenTelemetry + dashboards) and resiliency hardening (retries, dead-letter queues, chaos testing one service failure).

9. Interview Talking Points

  • Why an event-driven architecture over a monolith for this domain (independent scaling of ingestion vs. billing, natural audit trail of events, easier to add new consumers later).
  • Trade-offs you considered (e.g., choosing Kafka over a simpler message queue like RabbitMQ — throughput and replay-ability).
  • How idempotency and exactly-once-ish processing were handled given Kafka's at-least-once guarantees.
  • How you'd scale this to real meter volumes (partitioning strategy on meterId, consumer group scaling).
  • What you'd change for a real production deployment (multi-region, real payment processing, compliance).
