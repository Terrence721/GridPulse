# Architecture Decisions

Full decision-by-decision reasoning (context, alternatives, consequences) for design choices in this repo. `todo.md` and the wiki summarize and link here rather than duplicating it — this is the one place the complete reasoning lives.

## Meter Simulator configuration: field-supplied, never hardcoded

**Context.** Meter Simulator needs to know which street/block of meters it's simulating: a street name, a starting address, and how many buildings sit on each side. The initial implementation hardcoded a literal list of 28 meter IDs directly in `MeterSimulatorOptions`.

**Why that was wrong.** A real deployment's meter count and location vary per installation — baking any specific list (or even specific default values) into source code means every deployment either runs against fake data or requires a code change and redeploy just to point at a different street. Neither is realistic for a field-deployed system.

**Alternatives considered for "how does the value get set":**

1. **An interactive console prompt at startup**, asking the field engineer which street they're on. Rejected — `MeterSimulator` is a headless background worker; blocking process startup on console input doesn't fit that shape, and doesn't work at all under an orchestrator that isn't attached to a terminal.
2. **A single config listing multiple streets/blocks at once**, with the worker generating readings across all of them. Rejected — it doesn't match the real-world shape being modeled (one deployed instance = one field engineer's territory = one block), and it reintroduces the same "which literal values ship in the repo" problem, just as a list instead of a flat array.
3. **Config-per-deployment (chosen).** `StreetName`/`StartingAddress`/`BuildingsPerSide` are plain configuration values. One `MeterSimulator` instance covers one block; which block is just how that instance gets configured when it's deployed. `CityBlockMeterIdFactory` computes the actual meter-ID list (even side + odd side) from those three numbers at startup — nothing enumerated in source.

**The harder question: should the config values themselves have defaults?** The first pass gave `StreetName`/`StartingAddress`/`BuildingsPerSide` real-looking default values (`"MAIN-ST"`, `100`, `14`) directly in the C# class. Reconsidered: a default value baked into source is still hardcoding, even if it's "just a fallback" — it means a deployment that forgets to configure these will silently run against fake data instead of failing loudly.

**Decision:** no defaults, anywhere, for these three values. `MeterSimulatorOptions` marks them `[Required]`/`[Range]`; `builder.Services.AddOptions<MeterSimulatorOptions>().ValidateDataAnnotations().ValidateOnStart()` wires the validation in. The app now refuses to start at all — with a clean, specific error per missing field — rather than ever running with placeholder data.

**A real bug this surfaced:** the first fail-fast attempt technically worked (the app did exit non-zero with our own caught, clean error message) but a full stack trace printed first anyway. .NET's Generic Host logs `OptionsValidationException` internally during `IHost.StartAsync()`, before any caller's own try/catch around `host.Run()` ever sees it — so wrapping `host.Run()` in a catch isn't enough on its own. Fixed by resolving `IOptions<MeterSimulatorOptions>.Value` manually right after `builder.Build()`, *before* calling `host.Run()` — the validation now runs in application code, never reaching the Host's internal startup-failure logging path. Verified live: a run with zero configuration now produces exactly the three expected validation messages and nothing else.

**Consequence for `AppHost`:** once `MeterSimulator` required these values with no defaults, `AppHost`'s own `AddProject<...>("meter-simulator")` call had nothing to supply them, so a local orchestrated run would fail immediately. The first fix for this — `.WithEnvironment("MeterSimulator__StreetName", "MAIN-ST")` with literal values in `AppHost.cs` — was caught before committing as the same mistake relocated: hardcoding didn't get removed, it moved from `MeterSimulatorOptions.cs` to `AppHost.cs`. Replaced with Aspire's `builder.AddParameter(...)`, itself given no default value, which resolves from `AppHost`'s own configuration (`dotnet user-secrets set "Parameters:meter-simulator-street-name" ...`) — a store that lives outside the repo entirely (`%APPDATA%\Microsoft\UserSecrets\<UserSecretsId>\secrets.json` on Windows) and is never committed. If those secrets aren't set, `AppHost` itself now fails to start, the same fail-fast discipline one layer up.

**Why not `appsettings.Production.json`?** Considered and rejected. .NET's configuration precedence loads `appsettings.json` → `appsettings.{Environment}.json` → environment variables, in that order — so a real deployment's actual environment variables would override anything in a `Production` file anyway, making it dead weight at best. And there's no safe content for it: leaving it empty accomplishes nothing, and filling it with real-looking example values reintroduces the exact hardcoding this whole design eliminates.

**What this buys, and what it costs:** the real-world pattern this demonstrates — config supplied by the environment at deploy time, never baked into source, with the app failing loudly rather than silently running on fake data — is exactly how a real field deployment would work (a `systemd` unit's `Environment=`, a Docker `-e` flag, a Kubernetes `ConfigMap`). `dotnet user-secrets` itself is explicitly a local-development-only mechanism, not something a real deployment would use — but `MeterSimulator` doesn't know or care where its environment variables came from, so swapping the real mechanism in later (Phase 5, CI/CD) requires no code change here. The cost: three extra layers most portfolio projects skip (validation attributes, fail-fast wiring, Aspire parameters) for what could have been three lines with defaults — worth it here specifically because getting this pattern right, and visibly correcting it twice when it wasn't, is the point of demonstrating it.

## NAESB ESPI: core data model only, OAuth2 authorization layer skipped

**Context.** Green Button/NAESB ESPI (Energy Services Provider Interface) is the real US DOE-backed standard for customer energy-usage data export. The full spec has two logically separate halves: a data model (`UsagePoint`, `MeterReading`, `ReadingType`, `IntervalBlock`/`IntervalReading`) and an OAuth2-based third-party-authorization layer (`Subscription`, `Authorization`, `RetailCustomer`) letting a third party request a customer's consent before reading their data.

**Alternatives considered:**

1. **Full spec, including OAuth2 authorization.** Rejected — GridPulse has no authentication/authorization system anywhere today (every existing endpoint, across all four services, is unauthenticated). Building a complete OAuth2 grant-flow, token-issuance, and consent-management system for one read-only reporting feature would be wildly disproportionate to a codebase with zero auth surface anywhere else, and would need its own design work unrelated to ESPI itself — this repo has no `RetailCustomer`/user-identity concept at all; `AccountId` is the only identity primitive that exists.
2. **Core data model only (chosen).** Implements the real `UsagePoint`/`MeterReading`/`ReadingType`/`IntervalBlock`/`IntervalReading` resources, correct against the actual NAESB XSD's element order and real enum codes, as plain unauthenticated `GET` endpoints.

**Decision.** Ship the core data model only. Route shape is simplified from real ESPI's OAuth-gated `/Batch/Subscription/{id}/...` paths to plain `/espi/1_1/resource/UsagePoint/...` paths, but the resources themselves and their XML shape are real, not simplified.

**The real, honestly-documented consequence:** these endpoints let any caller read any account's usage data by `AccountId` with no access control whatsoever. That's a materially bigger privacy exposure than this repo's existing CRUD endpoints, because energy-usage privacy — what time someone is home, when they travel, appliance-level behavior inferable from interval data — is specifically the thing ESPI's real OAuth2 layer exists to protect. This is not a theoretical gap being flagged for completeness; it's a real, present exposure in this codebase today, accepted as an explicit scope decision rather than an oversight, and worth revisiting before any real deployment (which this project has never claimed to be).

**Never described as "Green Button Certified"** — that's a real certification mark requiring conformance testing by the Green Button Alliance, which this implementation has not undergone and does not claim.

**A related, concrete finding this feature surfaced (not caused):** building and live-verifying the `UsagePoint` collection endpoint exposed a pre-existing data-integrity bug — a long-forgotten orphaned `MeterSimulator` process (predating the "Meter Simulator configuration: field-supplied, never hardcoded" decision above) had left 19,888 legacy Kafka-sourced rows with an empty `AccountId` in the live database. See [#26](https://github.com/Terrence721/GridPulse/issues/26) and the `todo.md` entry for this feature for the full root-cause trace and fix.

## Stripe payment integration: test-mode Checkout, core payment-collection flow only

**Context.** `Billing` generates real invoices but never collected payment — the pipeline stopped at "here's what you owe." Real Stripe Checkout (test mode) plus webhook verification closes that loop, added alongside NAESB ESPI as the two features requested after Phase 3.

**A real scope conflict, resolved before implementation.** `README.md`/`SECURITY.md` both stated "no real payment processing" was out of scope. Real Stripe test-mode Checkout Sessions and webhook signature verification are real payment processing in every architecturally meaningful sense — just confined to test mode, no live card data, no real money movement. Both docs were updated to state this narrower, honest distinction rather than silently contradicting them or avoiding the feature.

**Alternatives considered for how payment gets initiated:**

1. Inline inside `InvoiceGenerator.GenerateAsync`, synchronously calling Stripe right after computing `AmountDue`. Rejected — that method currently has zero external HTTP dependencies (Kafka + Postgres only); injecting an external, rate-limited API call directly into the core invoice-generation hot path would let a Stripe outage block invoice generation itself.
2. **A new, independent consumer of the existing `billing.invoice.generated` event (chosen).** Mirrors the precedent `notification-service` already established (a separate consumer reacting to the same event). New `InvoicePaymentConsumer`/`InvoicePaymentInitiator` pair, matching `UsageAggregatedConsumer`/`InvoiceGenerator`'s existing consumer-plus-testable-POCO shape.

**A deliberate divergence from the existing consumer's own convention, and why:** `UsageAggregatedConsumer` uses `AutoOffsetReset.Earliest` safely, because replaying its topic's history just re-runs idempotent Postgres upserts. The new payment consumer uses `AutoOffsetReset.Latest` instead — `billing.invoice.generated` has real history since Phase 2, and `Earliest` would fire a real Stripe API call for every historical invoice on first startup, an external, rate-limited side effect, not a free internal upsert.

**PCI scope, a deliberate choice, not an accident.** Payment collection uses Stripe's hosted Checkout Sessions exclusively (never Stripe Elements, never raw card fields) — cardholder data never touches GridPulse code or servers, entered entirely on Stripe's own domain. This is what makes the integration SAQ-A-eligible in principle.

**Real Stripe API constraints discovered and designed around, not assumed:**

- Checkout Session-level `metadata` does not propagate to the underlying `PaymentIntent` — they're separate objects with separate metadata bags. `invoiceId` is set on both `SessionCreateOptions.Metadata` and `SessionCreateOptions.PaymentIntentData.Metadata` at creation time, so a `payment_intent.payment_failed` webhook (which only carries `PaymentIntent` metadata) can still be matched back to the invoice.
- Every `HttpClient` in this repo (including the new Stripe one) automatically gets `ServiceDefaults`' `AddStandardResilienceHandler()`. If Stripe's create-session call succeeds server-side but the response is lost to a client-side timeout, that resilience handler's retry-on-transient-fault would otherwise create a second, duplicate Checkout Session for the same invoice. Fixed with `RequestOptions.IdempotencyKey = invoice.Id.ToString()` on the create call, making any retry a safe no-op returning the original session — and `Stripe.net`'s own SDK-level retry (`SystemNetHttpClient`) is explicitly disabled (`maxNetworkRetries: 0`) so only one retry layer exists, not two stacked ones.
- `Stripe.net`'s `EventUtility.ConstructEvent` (the real webhook-signature-verification helper used, rather than hand-rolled HMAC) throws by default if the incoming event's `api_version` doesn't match the SDK's compiled version — the CLI-registered webhook endpoint must be configured to match whatever `Stripe.net` version is pinned in `GridPulse.Billing.csproj` (an exact version, matching this repo's existing pinning convention), or every webhook would 400.

**Migration approach — backfill, not delete, a deliberate deviation from `ReKeyInvoiceToAccountId`'s precedent.** That earlier migration deleted existing rows because the old column's *values* were meaningless under the new key (`MeterId` strings masquerading as `AccountId`s). The new `Status`/`StripeCheckoutSessionId`/`StripePaymentIntentId`/`PaidAt` columns are an orthogonal new fact about rows that are still valid financial records — deleting them would have been actively wrong, not just unnecessary. `AddColumn(..., defaultValue: "Open")` backfills every existing row as part of the same DDL statement.

**Idempotency, a deliberate simplification, flagged honestly.** The webhook handler guards `if (invoice.Status == "Paid") return;` once, before dispatching on event type — sufficient because the only two handled event types (`checkout.session.completed`, `payment_intent.payment_failed`) are mutually exclusive terminal states for one invoice, and Stripe redelivers events at-least-once and unordered the same way Kafka does. A full processed-Stripe-event-id deduplication table was considered and rejected as disproportionate to what two mutually-exclusive states actually need.

**A real bug found via live verification, its root cause traced with direct evidence, and fixed ([#27](https://github.com/Terrence721/GridPulse/issues/27)):** `InvoicePaymentConsumer` initially let a `Stripe.StripeException` propagate unhandled when a real invoice's `AmountDue` fell under Stripe's real $0.50 USD Checkout Session minimum — real hourly usage can legitimately be a small fraction of a kWh, so this is an expected case, not an edge case. Because .NET's default `BackgroundServiceExceptionBehavior` is `StopHost`, that one exception crashed Billing's *entire* host process, taking down `UsageAggregatedConsumer` — the pre-existing, Stripe-unrelated core invoice-generation consumer — as collateral damage. Fixed two ways: an explicit guard skips Stripe checkout session creation entirely for invoices under $0.50 (this business rule is a real, permanent Stripe platform constraint, not deployment config, so it's a literal with a WHY comment rather than an added configuration option), and the consumer's call into `InvoicePaymentInitiator` is now wrapped in a try/catch, so no future Stripe API failure (rate limit, transient network issue) can ever crash the host again either.

**A known, documented limitation, not solved this pass:** if an invoice's `AmountDue` changes via `InvoiceGenerator`'s existing upsert behavior *after* a Checkout Session has already been created for it, the pending Stripe session goes stale rather than being recreated or invalidated. Accepted as out of scope for this pass, the same way ESPI's OAuth skip was.

**Verified live, end to end, with real Stripe test-mode infrastructure — not just unit tests:** a real Checkout Session created via the real Stripe API for a real generated invoice, confirmed exact metadata (`invoiceId`), amount (`$1.60` matching `AmountDue` exactly), and success/cancel URLs; a real successful payment (Stripe's `4242 4242 4242 4242` test card) confirmed via `psql` to set `Status = 'Paid'`, a real `PaidAt` timestamp, and a real `StripePaymentIntentId`; a real declined payment (`4000 0000 0000 0002`) confirmed to set `Status = 'PaymentFailed'`; idempotency confirmed by resending the same Stripe event and observing an identical, unchanged `PaidAt` rather than a second processing; the pre-existing 293 invoices confirmed to backfill to `Status = 'Open'` correctly; `AppHost.Tests`' `CoreLoopSmokeTests` integration test (which boots the whole real distributed app, meter-simulator included) reconfirmed passing after the fix.

## Grid Operations: outage detection & work orders, split across two services

**Context.** Every feature up to this point modeled the *billing* side of a utility (meter → usage → invoice → payment). Nothing modeled the *field-operations* side — a downed wire, a blown transformer, a crew dispatched to fix it. Grid Operations adds that, fed by two paths: a tech filing a work order directly through a real HTTP form, and a genuine technical hook tying back into the existing Kafka pipeline — detecting a likely outage from real meter data, the way real AMI-based utility outage detection actually works.

**Alternatives considered — where detection logic lives:**

1. **All detection logic inside Grid Operations**, querying Usage Aggregation's `ProcessedReadings` table directly or over HTTP. Rejected — it would either reach across a service boundary into another service's database (breaking the bounded-context separation every other feature here has respected) or add a synchronous polling dependency Grid Operations shouldn't need.
2. **Split across two services (chosen).** Usage Aggregation — the service that already owns `ProcessedReadings` — detects the low-level signal ("this meter stopped transmitting") and publishes `usage.anomaly.detected`. Grid Operations consumes that event and owns the higher-level correlation/work-order logic. Matches this repo's existing publish-an-event-rather-than-reach-into-another-service's-data pattern used everywhere else.

**Alternatives considered — the detection signal itself:**

1. **Usage dropped near zero.** Rejected — the real UCI household dataset this repo replays legitimately produces near-zero readings for every meter overnight; a value-threshold signal would false-positive constantly on entirely normal data, not just during a real outage.
2. **Meter stopped transmitting readings at all (chosen).** `UsageAnomalyDetector`, a `PeriodicTimer`-driven `BackgroundService`, checks whether a meter's most recent reading is older than `ExpectedReadingIntervalSeconds × MissedIntervalMultiplier`. This is the real signal actual AMI-based utility outage detection uses — a meter that's lost power stops reporting entirely, rather than reporting a low value.

**Decision — correlation scope, an honest limitation, not a completeness gap glossed over.** `OutageCorrelator` groups quiet meters by street-number proximity (a configurable window) and a time window keyed on each anomaly's own `LastSeenAt`. Every deployment in this repo is one single configured street, so there's no multi-street topology to reason about — this is real, present scope, the same category of honest documented limitation as ESPI's OAuth2 skip above, not a theoretical gap.

**A real DRY correction, made while building this feature, not before it.** `CityBlockMeterIdFactory` had been deliberately duplicated identically across `MeterSimulator` and `AccountCustomer` since Phase 3 — initially defended the same way this repo's per-service Avro classes are (a working precedent elsewhere in the codebase). Challenged directly (*"why is that an acceptable trade-off"*) rather than accepted at face value: the Avro duplication has a real compensating safety net (Confluent Schema Registry's compatibility enforcement catches drift at publish time); `CityBlockMeterIdFactory`'s duplication had none — a silent edit to one copy and not the other would produce two services generating different meter-ID lists with no error anywhere. Extracted into `GridPulse.Shared`, referenced by both services — the first cross-service-referenced project in this repo besides `ServiceDefaults`, and a deliberate reversal of the earlier per-service-duplication convention for this one specific case, not a blanket policy change.

**Two real bugs found via live verification, both root-caused with direct evidence, both closed:**

- **[#29](https://github.com/Terrence721/GridPulse/issues/29) — outage correlation fragmented on 3+ simultaneous meters.** Stopping `meter-simulator` with 20 real meters active and letting them all go quiet together produced 5 separate 2-meter `Outage`s plus several orphaned standalone drafts sitting *inside* those outages' street-number ranges, instead of the one shared work order the design called for. Root cause: the correlator only ever paired a new anomaly with the single nearest existing draft, and never re-checked whether other already-existing drafts now fell inside a growing outage's range once it was created. Fixed by redesigning `OutageCorrelator` around two outcomes instead of one: extending an existing outage's range (absorbing any newly-in-range orphaned drafts) and merging a whole cluster of nearby drafts into one brand-new outage — either way keeping exactly one surviving `WorkOrder`, deleting the redundant ones. The fix also scopes the correlator's candidate query to `HazardType == SuspectedOutage`, so a tech-filed work order (any other hazard type) can never be silently merged or deleted by this background process — a real, separate risk noticed while designing the fix, not the original bug itself.
- **[#30](https://github.com/Terrence721/GridPulse/issues/30) — cold-start false positives.** On a fresh AppHost start, real leftover `ProcessedReadings` from a previous dev session (already older than the stale threshold) got flagged as brand-new anomalies on the detector's very first sweep — including the already-known `SMOKE-TEST-METER-*` rows from [#28](https://github.com/Terrence721/GridPulse/issues/28), confirming that pollution now reaches Grid Operations too, not just `accountsdb`. Fixed by adding `UsageAnomalyOptions.MaxAnomalyLookbackSeconds` (300 seconds) — a reading only signals a *new* anomaly if it's recent enough to mean "this meter was working until shortly before," not simply old, pre-existing data from before this run started.

**Verified live, end to end:** a real AppHost run with `meter-simulator` intentionally stopped to force real quiet meters, confirmed against real `gridoperationsdb` data via `psql` — both the single-meter-draft case and the multi-meter correlated-outage case; the fixed correlator and the cold-start lookback bound both re-verified live the same way after their respective fixes; full solution build (0 warnings/errors) and all 95 .NET tests + 7 Notification Service Vitest tests passing.

## Phase 4 split in two: the Grid Operations console ships before the customer billing dashboard

**Context.** The original design doc scoped Phase 4 as one thing: "React/Redux Toolkit dashboard + BFF/API gateway with OIDC auth." Direct inspection of the codebase at the start of this phase surfaced a real asymmetry between the two personas that thing actually serves — a field-crew/dispatcher console and a customer billing dashboard — that made building them as one combined effort the wrong call.

**Alternatives considered:**

1. **One dashboard, one BFF, covering both personas.** Rejected — the two personas need different data (work orders/outages vs. usage/invoices), different auth (a small set of internal dispatcher accounts vs. real customer accounts), and, concretely, different backend readiness: `GridOperations`' HTTP surface (`POST/GET /work-orders`, `PATCH /work-orders/{id}/status`, `GET /outages`) was already fully built and live-verified before this phase began, while `Billing` has no invoice list/read endpoint at all today (invoices are write-only via Kafka) and `UsageAggregation` only exposes ESPI Atom/XML, not JSON. Building one combined slice would have blocked the whole phase on new `Billing`/`UsageAggregation` endpoints that have nothing to do with grid operations.
2. **Two independent frontend+BFF pairs, Grid Operations console first (chosen).** Ship the slice with zero new backend endpoints needed first, proving the full auth + live-push architecture end-to-end fastest; the customer billing dashboard becomes its own later plan cycle once its backend gaps are closed.

**Decision.** This document, and every design decision below it referencing "Phase 4," covers the Grid Operations console only. The customer billing dashboard is deferred, tracked separately in `todo.md` (Phase 8b) and issue [#13](https://github.com/Terrence721/GridPulse/issues/13).

## Grid Operations console auth: Duende IdentityServer, and why its Quickstart UI is Razor Pages, not React

**Context.** No authentication exists anywhere in this repo today — every endpoint, in every service, is anonymous. The Grid Operations console is the first feature requiring real login, so the OIDC provider choice is being made for the first time here.

**Alternatives considered:**

1. **Keycloak (`Aspire.Hosting.Keycloak`).** A real, official Aspire hosting integration exists, but every published version is still preview-only, and Keycloak itself is a full JVM container — disproportionate operational weight (and cold-start time) for a demo whose entire login surface is a handful of dispatcher accounts.
2. **OpenIddict.** A legitimate, fully open-source .NET option requiring no separate container. Rejected specifically because it ships no login/consent UI at all — every screen would need to be hand-built, and no prior Aspire-paired sample exists to follow.
3. **Duende IdentityServer (chosen).** Requires no special Aspire hosting package — it's `builder.AddProject<Projects.GridPulse_Identity>("identity")`, exactly like every other .NET project in this repo (Duende's own official samples repo demonstrates this same AppHost-launches-IdentityServer-alongside-clients pattern). Free for development/test and non-commercial/personal projects — sufficient here.

**Why the login pages are Razor Pages, when the rest of this feature is a React SPA.** This is not an inconsistency in the frontend stack — the identity provider's login/consent screens are not part of GridPulse's own UI at all. In OIDC's Authorization Code + PKCE flow (what this feature uses), a browser SPA never renders its own login form; that's the deprecated Resource Owner Password Credentials anti-pattern, explicitly disallowed under current OAuth security guidance for public clients. Instead, the browser is redirected away from the React app to the identity provider's own hosted login page — on its own origin, served by whichever OIDC provider is chosen — and redirected back with an authorization code once the user authenticates. Every OIDC provider (Duende, Keycloak, Auth0, Okta) serves this hop the same way; it's a separate concern from the client application's own stack, not a technology choice about the dashboard.

Duende's official project template happens to implement that hosted UI as ASP.NET Core Razor Pages, because login/consent/logout is genuinely just a handful of server-rendered forms needing session/cookie handling, CSRF protection, and password verification — nothing that benefits from being a richer client-side app. Scaffolding `src/Identity` from Duende's own `isinmem` template (rather than hand-building this UI) is a deliberate, narrow exception to this repo's usual from-scratch scaffolding habit: login/consent is a security-sensitive surface (anti-forgery tokens, secure cookie handling, password hashing) where reimplementing it by hand for a demo adds real risk for no benefit — it wouldn't showcase anything the React/Redux Toolkit work doesn't already demonstrate.

**A real, present trust-boundary decision, stated honestly.** `grid-operations` itself gains no authentication of its own in this slice — it remains exactly as anonymous as it is today. Only the gateway's JWT-bearer check stands between the public network and a real work-order mutation; `grid-operations` trusts that only the gateway (inside the same Aspire-orchestrated private network) ever calls it. An accepted, explicit trade-off for this slice, not an oversight — revisit before any real deployment.

## Live push via a BFF-side SignalR relay of `usage.anomaly.detected`

**Context.** A dispatcher watching the console needs to know the instant a meter goes quiet, not on the next manual refresh — the same real-time expectation a real utility's outage-management system has to meet.

**Alternatives considered:**

1. **The browser subscribes to Kafka directly.** Rejected outright — there is no browser Kafka client, and even if there were, it would mean handing an untrusted public client direct network access to the internal Kafka broker and Schema Registry, a much larger exposure than anything else in this repo's trust model.
2. **A BFF-side relay over SignalR (chosen).** `GridOperationsGateway` runs its own `AnomalyRelayConsumer`, a `BackgroundService` structured like `GridOperations`' own `UsageAnomalyConsumer` minus the correlation logic, under its own consumer group (`grid-operations-gateway`, independent of `GridOperations`' `grid-operations` group — each gets a full, independent copy of the topic) and broadcasts each anomaly to every connected browser via `AnomalyFeedHub`.

**Why `AutoOffsetReset.Latest`, not `Earliest`, on this consumer.** There is no "meter came back" event on this topic — only "meter went quiet." Replaying its full history on every relay startup or consumer-group reset would flood every newly-connected dashboard session with a backlog of stale anomalies, some possibly already resolved. `Latest` means the live feed only ever shows anomalies detected while the relay has actually been running — the same reasoning already applied to `Billing`'s `InvoicePaymentConsumer` for `billing.invoice.generated`, and to `Notification Service`'s consumer of that same topic (see above).

**Deliberately no address enrichment on the relay.** `GridOperations`' own `WorkOrderCorrelationProcessor` already looks up the meter's street address moments later, if and when the anomaly becomes a real `WorkOrder`. Duplicating that `account-customer` lookup here, for a transient feed entry that may never become a work order, was judged not worth a second dependency on that service — the live feed shows `meterId`/`accountId`/`lastSeenAt` only; the enriched, durable record is the `WorkOrder` itself.

**Auth on the hub matches the REST endpoints, with one necessary adjustment.** `AnomalyFeedHub` is `[Authorize]` under the same JWT bearer scheme `GridOperationsGateway`'s REST endpoints use. SignalR's WebSocket/SSE transports can't attach an `Authorization` header to their handshake, so the client instead appends the token as `?access_token=...`; `AddGatewayAuthentication`'s `OnMessageReceived` pulls it into `context.Token`, but only for requests under `/hubs` — REST calls still authenticate the normal header way.

**A known, honestly-stated limitation.** There is no replay buffer. A dispatcher who wasn't connected at the moment an anomaly fired will never see it via this feed — only the real `WorkOrder`/`Outage` rows, populated independently by `GridOperations`' own correlator, are the durable source of truth. The live feed is a convenience layer on top of that, not a second copy of it.
