One IRatePlan interface, three real pricing strategies.

InvoiceGenerator never branches on which plan applies — it calls CalculateCost(hourlyUsage) on whichever IRatePlan implementation BillingOptions.DefaultRatePlanType resolves to. A real Strategy pattern, not a switch statement wearing an interface.

public interface IRatePlan {
  decimal CalculateCost(IReadOnlyList<HourlyUsageSnapshot> hourlyUsage);
}
Rate plan Real config How the cost is computed Worth knowing
Flat FlatRatePerKwh = 0.16 Sums every hour's TotalKwh, multiplies by one flat rate The only plan that never needs to look at an individual hour's timing — total usage is all it needs
Tiered Tiers: 500 kWh @ 0.14, next 500 @ 0.17, remainder (to 100,000) @ 0.21 Walks tiers in order, consuming each bracket's remaining capacity before spilling into the next — the final bracket is open-ended The exact tier-boundary case (usage landing precisely on a threshold) has its own dedicated test — the easiest place for an off-by-one to hide
Time of Use PeakRatePerKwh/OffPeakRatePerKwh = 0.22/0.10, window 14:00–19:00 Classifies each HourlyUsageSnapshot individually by hour-of-day against the configured peak window The only plan needing per-hour granularity at all — correctly handles a peak window that wraps past midnight, not just the daytime case that's easy to get right by accident

A real simplification, not an oversight: which plan applies is one deployment-wide config value (BillingOptions.DefaultRatePlanType), not a per-account choice — there's no Account.RatePlanType column anywhere. A real billing system would let each customer be on a different plan; that's explicitly out of scope here, the same honest-scope-decision pattern used for ESPI's OAuth skip — see the ESPI + Stripe diagram.
