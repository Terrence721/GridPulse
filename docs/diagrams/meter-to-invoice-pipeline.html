GridPulse — meter-to-invoice pipeline

Every reading goes through the same seven steps.

The full sequence, from a simulated kWh reading to a delivered webhook and an initiated Stripe payment. Three steps — idempotency/rollup, rate-plan selection, and the fan-out at the end — are zoomed into below, since each involves a real design decision worth understanding on its own.

Generate Reading→ Produce meter.readings.raw→ Idempotency + Hourly Rollup→ Produce usage.aggregated→ Apply Rate Plan→ Produce billing.invoice.generated→ Fan Out: Webhook + Stripe

Zoomed In

Usage Aggregation

A duplicate reading is a no-op, not a double-count

Every reading carries a ReadingId. ReadingProcessor checks ProcessedReadings for it first — its existence is the idempotency check, not a side effect of one. Only a genuinely new reading updates the (AccountId, PeriodStart) hourly bucket, summing Kwh into the running total. Kafka's at-least-once delivery means this isn't theoretical: real duplicate deliveries are a normal, expected condition here, not a failure mode.

A real migration behind that key: HourlyUsage was originally keyed by MeterId — no Account/Customer Service existed yet to map a meter to an account. Phase 3 re-keyed it to AccountId for real, and the migration deleted the old rows rather than carrying forward data meaningless under the new key.

Billing

One interface, three interchangeable pricing strategies

IRatePlan.CalculateCost(hourlyUsage) is implemented by FlatRateRatePlan, TieredRatePlan, and TimeOfUseRatePlan — a real Strategy pattern, not an if/switch chain hiding inside one class. InvoiceGenerator applies whichever plan BillingOptions.DefaultRatePlanType configures, then upserts the Invoice for that (AccountId, PeriodStart, PeriodEnd, RatePlanType) — an upsert, not an insert, because usage.aggregated republishes continuously as an hour's usage accumulates.

Post-Phase-3 addition

Two independent consumers of one event, added without touching the producer

billing.invoice.generated now has two consumers that have never met each other: Notification Service (Phase 3, delivers the real webhook) and the Stripe payment consumer (post-Phase-3, creates a real Checkout Session). Both react to the exact same event; InvoiceGenerator was never touched to add either one.

A real, deliberate divergence between them: the Stripe consumer uses AutoOffsetReset.Latest, not Earliest like every other consumer in this repo — this topic has real history since Phase 2, and replaying it on Earliest would fire a live Stripe API call for every historical invoice on first startup.
