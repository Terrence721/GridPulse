GridPulse — outage detection & correlation

From a quiet meter to a real work order, in seven steps.

Grid Operations' auto-detection path, end to end — a tech filing a work order directly through POST /work-orders skips straight to the last step. Three steps — the detection signal itself, the correlation decision, and the status lifecycle — are zoomed into below, since each involves a real design decision (and, for two of them, a real bug found via live verification).

Meter Stops Transmitting→ Detect Anomaly→ Produce usage.anomaly.detected→ Resolve Street Address→ Correlate Into Outage→ Create/Extend Outage + Work Order→ Status Lifecycle & Dispatch

Zoomed In

Usage Aggregation

The signal is "stopped transmitting," not "usage dropped"

UsageAnomalyDetector, a PeriodicTimer-driven BackgroundService, checks every SweepIntervalSeconds for any meter whose most recent reading is older than ExpectedReadingIntervalSeconds × MissedIntervalMultiplier. A value-based threshold ("usage near zero") was considered and rejected — the real UCI household dataset this repo replays legitimately produces near-zero readings for every meter overnight, which would false-positive constantly on entirely normal data.

A real bug found via live verification: on a fresh AppHost start, leftover ProcessedReadings from a previous dev session — already older than the threshold — got flagged as brand-new anomalies immediately, including the already-known SMOKE-TEST-METER-* rows from issue #28. Fixed with UsageAnomalyOptions.MaxAnomalyLookbackSeconds: a reading only signals a new anomaly if it's recent enough to mean the meter just went quiet, not simply old data — issue #30.

Grid Operations

One shared outage, not one work order per affected meter

UsageAnomalyConsumer resolves the real street address via a live HTTP call to Account/Customer Service, builds a DetectedAnomaly, and hands it to OutageCorrelator — pure decision logic, no DB access, directly unit-testable — which returns one of four outcomes: AlreadyCovered (this meter's street number already falls inside an open outage, or it already has its own draft), CreateDraft (nothing nearby), CreateOutage (a cluster of nearby drafts merges into one new outage), or ExtendOutage (an existing outage's range grows to absorb this anomaly, and any other now-in-range orphaned drafts). Proximity is a configurable window (GridOperationsOptions.CorrelationAddressWindow/CorrelationTimeWindowSeconds) keyed on each anomaly's own LastSeenAt. WorkOrderCorrelationProcessor then applies whichever decision comes back, writing the real WorkOrder/Outage rows.

A real bug found by stopping 20 real meters at once: the first version only ever paired a new anomaly with the single nearest existing draft, never re-checking whether other drafts now fell inside a growing outage's range. Live-verified result: 5 separate 2-meter outages plus several orphaned standalone drafts sitting inside those outages' ranges, instead of one shared work order. Fixed by adding the ExtendOutage/CreateOutage split above, keeping exactly one surviving WorkOrder either way, deleting the redundant ones — issue #29.

WorkOrder

A tech can file one directly too — auto-detection isn't the only path in

POST /work-orders is a genuinely fillable form, not just a ticket stub: a real HazardType (DownedWire, BlownTransformer, BrokenPole, VegetationContact, EquipmentFailure, VehicleAccident, WeatherDamage, AnimalContact, or SuspectedOutage for an unconfirmed auto-detected draft), an optional MeterId/address, a description, and an assigned crew. Status moves Reported → Dispatched → EnRoute → OnSite → Repaired → Restored → Closed, plus Ignored from Reported only (a false-positive auto-detected draft).

Validation lives in a plain WorkOrderStatusTransitioner/WorkOrderStatusUpdater pair, never on the entity itself — matching this repo's existing anemic-POCO-plus-processor-class shape (InvoiceGenerator, ReadingProcessor). The background correlator is explicitly scoped to HazardType == SuspectedOutage drafts only, so a tech-filed work order can never be silently merged or deleted by it.

i

Correlation is street-number-proximity only — every deployment here is one single configured street, so there's no multi-street topology to reason about. A real, present limitation, not a completeness gap glossed over. See the System Architecture diagram for where Grid Operations sits relative to the rest of the pipeline, and docs/architecture.md for the full design reasoning.
