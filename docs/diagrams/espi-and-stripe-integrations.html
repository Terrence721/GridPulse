GridPulse — post-Phase-3 features

Two Kafka-only services, each gaining real HTTP for the first time.

Usage Aggregation and Billing had shed their original REST endpoints back in Phase 2 — both were pure Kafka consumer/producers until these two features. Neither reintroduced REST for its own sake; each added exactly the HTTP surface its real-world standard actually requires.

Billing + 1 webhook receiver, + 1 new Kafka consumer Real Stripe test-mode payment collection

Zoomed In

Usage Aggregation

Real NAESB ESPI resources, real enum codes, one deliberate omission

Five endpoints under /espi/1_1/resource/UsagePoint/... serve real UsagePoint/MeterReading/ReadingType/IntervalBlock Atom XML feeds — real XSD element order, real enum codes (uom=72 Wh, since ESPI has no "kWh" unit at all). The OAuth2 third-party-authorization half of the real spec is deliberately not implemented — this repo has no authentication system anywhere — documented with its honest consequence: any caller can read any account's usage by AccountId, no access control.

A real bug this surfaced, not caused: the new collection endpoint exposed a phantom account with an empty id — 19,888 rows left by a long-forgotten orphaned MeterSimulator process from before account enrichment existed, traced with direct evidence (the current code physically cannot produce this) rather than assumed, then fixed three ways — issue #26.

Billing

Real Stripe API constraints, discovered from the real SDK source, not assumed

  • Checkout Session metadata doesn't propagate to the underlying PaymentIntent — set on both objects, or a failed payment silently vanishes
  • Every HttpClient here inherits a retry handler that could create a duplicate Checkout Session on a lost response — fixed with a real Stripe IdempotencyKey
  • EventUtility.ConstructEvent throws on a webhook API-version mismatch — made an explicit, checked precondition, not a silent landmine

A real bug this caused, found and fixed: a real invoice under Stripe's actual $0.50 minimum crashed Billing's entire process — .NET's default BackgroundServiceExceptionBehavior is StopHost, so one Stripe rejection took the pre-existing, Stripe-unrelated invoice pipeline down with it. Caught by the full-stack integration test, fixed with an explicit amount guard plus a try/catch — issue #27.
