### Meter Simulator — real dataset replay (orthogonal quality improvement, not a Phase 3 step)

Meter Simulator generated purely synthetic readings since Phase 1 (`Math.Round(_random.NextDouble() * 5, 3)` kWh per tick) — a made-up number with no connection to real household electricity use. Replaced with a replay of a real, published dataset: [UCI's *Individual Household Electric Power Consumption*](https://archive.ics.uci.edu/dataset/235/individual+household+electric+power+consumption) (Hebrail & Berard, 2012, CC BY 4.0) — real minute-level power measurements from one household in Sceaux, France, December 2006–November 2010. The full archive is ~127MB, exceeding GitHub's 100MB file limit, so a real, complete, unmodified February 2007 excerpt (40,318 rows after dropping 2 rows with missing values, trimmed to just the `Date`/`Time`/`Global_active_power` columns GridPulse actually uses) was extracted and checked in directly as `src/MeterSimulator/Data/power-data-february-2007.json`, with full attribution in `src/MeterSimulator/Data/SOURCE.md`.

Three deliberate design decisions: **(1)** `Global_active_power` is real power in kilowatts, not energy — `MeterReadingGenerator` converts it to a real per-tick kWh amount (`kw × intervalSeconds / 3600`), which is both dimensionally honest and fixes a latent implausibility in the old random generator (up to 5 "kWh" every 5 seconds was physically absurd). **(2)** Readings still stamp `DateTimeOffset.UtcNow` at publish time, not the dataset's original 2007 date — every downstream consumer (hourly rollup, invoicing, the smoke test) already assumes readings arrive close to real time, so this keeps the change isolated to Meter Simulator. **(3)** Each of the 28 meters gets its own cursor into the same 40,318-row sequence (seeded via `Math.Abs(meterId.GetHashCode()) % dataset.Count`, advancing and wrapping per reading), so all 28 show real recorded values at different real points in the same real month rather than 28 identical echoes.

Re-verified live via direct Postgres inspection (not a separate consumer script — `Worker.cs`'s existing per-reading log line was deemed sufficient, and checking `ProcessedReadings` directly was simpler still): real converted values landing (e.g. `0.000306`, `0.002939`, `0.008706` kWh across different meters at the same moment — a dramatic, correct departure from the old 0-5 random range), genuinely different per meter, and changing *gradually* tick-to-tick for a given meter (e.g. `0.000306 → 0.000306 → 0.000303 → 0.0003`) rather than jumping randomly — exactly the character of real household consumption (a stable baseline load during what's likely a real overnight period in the dataset), which the old pure-random generator could never produce. `MeterReadingGeneratorTests` rewritten for the new constructor/signature (18 tests now, up from 17), including a new deterministic test asserting the exact kW→kWh conversion against a known real dataset value.

Deliberately **deferred**, not built here: a monthly GitHub Actions job to cycle through the archive's other real months (only one month fits under GitHub's file-size limit), and a daily per-account billing-cycle feature tied to the dataset's real calendar dates — both need their own separate plan.

### Dev-loop start/stop scripts (deferred from Phase 3, now complete)

Phase 3 step 10's live verification needed to force-kill the AppHost mid-run (an agentic session has no real interactive terminal to press Ctrl+C in), which orphaned every container and process it had spawned — manual cleanup that surfaced a real gap: nothing in this repo verified the stack came up genuinely healthy, or guaranteed it went down cleanly. `scripts/run-app.ps1` runs the AppHost in the foreground (so a real Ctrl+C reaches it directly, letting Aspire's own graceful shutdown work exactly as it would if a developer ran `dotnet run` by hand) and always runs `scripts/stop-app.ps1` afterward in a `finally` block — a safety-net sweep that fires automatically no matter how the run ends, clean or not, with no separate cleanup step to remember.

The real design challenge was scoping that sweep safely: this dev machine runs several other Aspire-based portfolio projects that also use resource names like `kafka`/`postgres`, so name matching alone risks killing an unrelated project's containers. Found via direct inspection that Aspire's DCP stamps every container it creates with a `com.microsoft.developer.usvc-dev.mountsLabel` naming its actual data volume (`gridpulse.apphost-<hash>-...` — unique to this project) and a `com.microsoft.developer.usvc-dev.creatorProcessId` (the `dcp` orchestrator's own PID) shared by every container *and* every OS process from that run. `stop-app.ps1` anchors on the volume-mount label to positively identify this project's containers, then uses that same run's `creatorProcessId` to find and recursively kill the entire process tree it spawned (a single AppHost run's `dcp` process turned out to parent **29 descendant processes** — far more than expected, confirming a flat "kill the direct children" approach wouldn't have been enough).

**Real bug found and fixed while building it:** the first version of `stop-app.ps1` failed to parse at all (`The string is missing the terminator`) — Windows PowerShell 5.1 reads a script written without a BOM using the system ANSI codepage, misinterpreting the UTF-8 em-dash characters used in its own comments and corrupting every string literal after them. Fixed by using plain ASCII punctuation throughout. Verified live twice: the no-op case (nothing running) reports cleanly, and the real safety-net case — killing the AppHost's `dotnet run` process out from under `run-app.ps1` to simulate a crash — confirmed the `finally` block fires automatically and the sweep correctly stops every container and process the run had spawned, leaving nothing orphaned.

**Extended to every start method, not just the script:** `run-app.ps1`'s cleanup only fires for runs started *through it*. Added a second layer directly in `AppHost.cs` — an `IHostApplicationLifetime.ApplicationStopping` callback that shells out to the same `stop-app.ps1` — so a graceful stop reaches the same cleanup whether the AppHost was started via Visual Studio's F5, a plain `dotnet run`, `aspire run`, or the script. Documented honestly, not oversold: neither this hook nor the script's `finally` can intercept a genuine forceful kill (Task Manager, `taskkill /F`, a crash) — that bypasses all in-process code by OS design, no matter where the hook lives. `stop-app.ps1` stays available to run manually for that case.

**A real design flaw caught by asking "what happens if this fails":** the first version of `stop-app.ps1` found *which processes* to kill by first finding this project's containers, then reading their shared `creatorProcessId` label. If Docker itself isn't reachable, that lookup returns nothing — which meant process cleanup silently got skipped too, in exactly the scenario (something's already gone wrong) where it matters most. Fixed by identifying processes independently of Docker entirely: every dotnet/node process this AppHost spawns has the repo's own path in its command line (e.g. `dotnet run --project ...\GridPulse\src\AccountCustomer\...`), which stays safely scoped away from this machine's other Aspire-based projects (they reference their own different repo paths) without depending on Docker being up at all. Verified live: killing a full 5-service run this way correctly found and stopped all **29 processes** in one pass, entirely independent of the separate container-label sweep.

**A second real bug found while hardening it:** adding a timeout around each `docker` call (so an unresponsive daemon can't hang the whole script) first used .NET's `ProcessStartInfo.ArgumentList` directly — which turned out to be `$null` by default under Windows PowerShell 5.1's .NET Framework base rather than a ready-to-use collection, so `.Add(...)` threw and every `docker` call silently ran with zero arguments. Caught by testing the exact pattern in isolation before trusting it, not by assuming it would work. Fixed by using a `Start-Job`/`Wait-Job -Timeout` pattern instead — PowerShell's own idiomatic way to time out an external command, verified working before it went into the real script. The WMI process-tree walk and the C# shell-out are both wrapped in their own `try`/`catch` too, so a failure in either reports a message and moves on rather than aborting the whole sweep or bubbling an unhandled exception into the AppHost's own shutdown sequence.
